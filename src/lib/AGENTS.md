# Server authentication
- Two-step sign-in is switched only by platform_settings.mfa_enforced (OFF in this build): mfa_session_ok() binds verification to the JWT session_id and drives restrictive RLS on private tables/buckets, the global requireMfaSession gate (allow-list in mfa-gate.ts) and the portal gates. Why: UI, server and database can never disagree; see docs/two-step-enforcement.md.
- MFA flow tables retain service-only INSERT/UPDATE/DELETE and are exempt from the two-step policy. Why: the code flow must work before verification.

# Document AI and onboarding
- Email checks use email-validation's bounded caller-specific modes and linear header/chip parsing. Why: prevent excessive regex work while preserving normal-address rules.
- Contract/conversion invoice defaults reserve numbers with collision-aware mint_billing_doc_number; draft labels use billing-number's Web Crypto generator; databaseError maps only the invoice-number unique index to billing-number's shared refusal. Why: every invoice write shares database-enforced uniqueness and friendly errors without affecting quotes.
- Billing payment status is database-derived; partial invoices keep unpaid balances via billing helpers; only cron sweeps overdue invoices. Why: receipts never imply full settlement or trigger global reader writes.
- Uploader/manager names use profile-name, billing resets use billing-brand, and absent invite actor emails omit the RPC argument to invoke SQL DEFAULT NULL. Why: typed contracts match stored data.
- Agency response reminders merge agency-scoped completed private declines with public responses via connection-response. Why: notify actual responses without leaking unanswered account matches.
- Document AI: Parserly is reached only through src/lib/parserly.server.ts (analyseDocument/pollAnalysis); document_ai_analyses is written only by src/lib/document-ai.server.ts with the service role, which checks the requester's own profiles.ai_filing_enabled on the server before any file is sent. Why: one integration point, and a switched-off user's files can never leave TalVault.
- Onboarding duplicate names and blocked-row display use onboarding-documents; service-only insert triggers replace blocked rows atomically and queue old objects, and draft screens retain their staging session. Why: corrected files never erase valid files or hide missing slots.
# Reporting
- Admin launch reports compute every figure through src/lib/launch-reporting-core.ts (SAST day boundaries), loaded by launch-reporting.functions.ts; launch targets/offer live only in platform_settings key "launch". Why: tested figures, editable targets.
- Real vs test accounts: agencies.is_test / talent_profiles.is_test, changed only by setAccountTest (audited); the real/test/all scope rule lives in src/lib/account-filters.ts (reports default to real) and launchOffer never allocates places to test accounts. Why: test data must never inflate launch figures or use offer places.
- Admin Reporting scope (Real/Test/All, `accounts` search param) and invitation funnels (drafts never sent; connection requests separate) come only from src/lib/report-scope.ts via loadTestScope; accepting a test-counted invitation flags the new account is_test by database trigger. Why: test runs never inflate real figures.
- Terms acceptance reports (Admin acceptances and not-accepted lists) leave out Test accounts via testUserIds in src/lib/terms-gate-core.ts; the acceptances are still stored with the normal proof. Why: test data must never inflate Terms or launch figures.
